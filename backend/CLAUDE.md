# CLAUDE.md (backend)

This file provides guidance to Claude Code when working in `backend/`.

Node/Express API using Knex (sqlite3 for dev/test, mysql2/pg supported), bcrypt + JWT auth in httpOnly cookies, CSRF double-submit protection, RBAC, rate limiting, and pluggable auth providers (local/WordPress/Wagtail). Uses Node's native `#alias/*` subpath imports (see `imports` in `backend/package.json`) instead of relative `../../` paths — `#config/*`, `#db/*`, `#middleware/*`, `#routes/*`, `#controllers/*`, `#services/*`, `#utils/*`, `#validators/*`.

## Commands (run from `backend/`)

```bash
npm run dev              # start with --watch
npm run start            # start (no watch)
npm run migrate          # knex migrate:latest
npm run migrate:rollback
npm run migrate:make <name>
npm run seed              # knex seed:run
npm run lint / lint:fix
npm run format             # prettier --write
npm test                   # vitest run
```

To run a single test file: `npx vitest run src/tests/leads.test.js`. Tests run with `fileParallelism: false` (`vitest.config.js`, at the **backend package root** — Vitest only auto-discovers config there, not in `src/`, so don't move it back) because they share a SQLite file — without it, test files race on the same `knex_migrations_lock` row and fail with `MigrationLocked`. Tests point at `./data/test.sqlite3` automatically (`NODE_ENV=test` in `src/config/env.js`), separate from dev data.

**The standard test suite only ever runs against SQLite** — it cannot catch a bug that only manifests on Postgres/MySQL (this happened for real: `auditedRepository.js`'s `insert()` destructured `.insert()`'s return value assuming sqlite3's shape, which crashed every single insert on Postgres — invisible to 179 passing sqlite-backed tests at the time). `src/tests/auditedRepository.pg.test.js` is this project's pattern for driver-specific regressions: `describe.skipIf(process.env.DB_CLIENT !== 'pg')`, skipped (with a visible placeholder test so it's not silently absent) under the normal `npm test`, and run for real with `DB_CLIENT=pg npx vitest run src/tests/auditedRepository.pg.test.js` against an actual Postgres database — never production. Follow this pattern for any future fix that's specifically about cross-driver Knex behavior.

**Current status**: 192/194 passing under the standard `npm test` (sqlite) — the 2 "skipped" are `auditedRepository.pg.test.js`'s real assertions, which only run under the `DB_CLIENT=pg` invocation above; the file's placeholder test (which does run under `npm test`) is one of the 192. See `frontend/CLAUDE.md`'s Testing section for the frontend's own count and the Playwright e2e suite.

## Architecture

Request flow: `routes/*.routes.js` → `middleware` (`authenticate`, `authorize`, `verifyCsrfToken`, `validate`/`validateBody`) → `controllers/*.controller.js` → `services/` (repositories / business logic) → Knex (`db/knex.js`) → SQLite/MySQL/Postgres.

- **Auth**: access + refresh tokens are issued as httpOnly cookies (`auth.controller.js`), never in the JSON body or any client-readable storage — this is the whole point of the backend and must not regress, even for debugging. A parallel non-httpOnly `csrf_token` cookie is set alongside them (`middleware/csrf.js`); mutating requests (POST/PUT/PATCH/DELETE) must include a matching `X-CSRF-Token` header via `verifyCsrfToken`. `authenticate` verifies the access token and attaches `req.user = { id }` (from the JWT, no DB hit) — role/permissions are deliberately **not** in the token, see RBAC below. Controllers needing the full profile call `userRepository.findById` themselves.
- **Auth providers** (`services/authProviders/`): `local`, `wordpress`, `wagtail`, selected by `AUTH_PROVIDER` env var via `getAuthProvider()`. All three must return the same `{ user }` shape from `register()`/`login()` and mirror the identity into the local `users` table via `userRepository.create({ ..., roleKey })` (`roleKey` defaults to `'member'`) — RBAC and everything downstream depends on that row existing.
- **Forgot/reset password**: `POST /auth/forgot-password` always returns the same generic message regardless of whether the email is registered — never leak which emails exist. For a matching *local*-provider user it issues a token via `tokenService.issuePasswordResetToken` (only its SHA-256 hash is stored, in `password_reset_tokens`, `PASSWORD_RESET_TOKEN_EXPIRES_IN`-configurable expiry, default 1h; issuing a new token invalidates the user's prior unused one) and emails a reset link through `emailService`. `POST /auth/reset-password` validates + single-use-consumes the token (`tokenService.consumePasswordResetToken`), updates `password_hash`, clears `must_change_password`, and calls `tokenService.revokeAllUserSessions` so every other logged-in session (not just this request, which isn't authenticated) is forced to re-login.
- **Forced password change**: admin-created users (`user.controller.js`'s `createUser`) get a system-generated temporary password — emailed via `emailService`, never returned in the API response — and `must_change_password: true`. `middleware/enforcePasswordChange.js` is mounted once, globally, in `app.js` (right after `cookieParser()`, before any router) rather than added per-route, so no route can forget it; it does its own lightweight token decode and, if `must_change_password` is set, blocks every request with `403 { message, errors: { code: 'MUST_CHANGE_PASSWORD' } }` except a small allowlist (`PATCH /users/me/password`, `POST /auth/logout`, `GET /auth/me`, `POST /auth/refresh`). `changePassword` (same endpoint used for ordinary self-service password changes) clears the flag on success.
- **Email**: `services/emailService.js` wraps nodemailer behind one function, `sendEmail({ to, subject, html, text })` — every caller (forgot-password, the admin-create-user welcome email, the settings "Send test email" action) goes through that, never nodemailer directly. SMTP config is a soft setting layered over the `EMAIL_*` env vars, not read from `env.js` directly: `getEmailConfig()` merges `smtp_host`/`smtp_port`/`smtp_secure`/`smtp_username`/`smtp_password`/`smtp_from` (via `settingsRepository`) over `config.email.*`, with a blank string or `0` meaning "not set in the DB, use the env var" for every field except `smtp_secure` (a boolean has no natural "unset" state, so it's seeded once from `EMAIL_SECURE` and the DB row is authoritative from then on — see `db/seeds/02_settings.js`'s comment). Because settings can change at runtime, the transporter is rebuilt from the merged config on every `sendEmail()` call rather than cached once. `smtp_password` is never echoed back by `GET /admin/settings` regardless of caller — even the `demo` role holds `settings:read` — see `settings.controller.js`'s `SENSITIVE_KEYS`; its audit log entries record that the value changed without logging the value itself. `POST /admin/settings/test-email` (same `settings:manage` gate as editing settings) sends a real email to the caller's own address using the current merged config, so an admin can confirm it actually works without checking server logs. Defaults to Mailpit (`localhost:1025`, no auth) for local dev. In `NODE_ENV=test` it swaps to nodemailer's built-in JSON transport (no real SMTP needed, no settings/DB lookup at all) and records what was "sent" via `_getSentEmailsForTests()`/`_clearSentEmailsForTests()` so tests can assert on email content (e.g. extract a temp password or reset link) without a real inbox.
- **RBAC — permission-based, not role-based**: `users.role_id` (FK) → `roles` (`admin`/`manager`/`member`/`demo`) → `role_permissions` (composite PK, cascade-deletes) → `permissions`. Starter permission keys: `users:read`, `users:write`, `users:delete`, `roles:read`, `roles:manage`, `settings:read`, `settings:manage`, `audit:read` — note `roles:*` and `settings:*` are split into a `:read` tier (view) and a `:manage` tier (create/edit/delete or change) rather than one all-or-nothing permission, specifically so a role like `demo` can view those admin sections without being able to change anything in them. `authorize('perm1', 'perm2', ...)` (`middleware/authorize.js`) requires **all** listed keys (AND, not OR) and loads them fresh from the DB on every request via a join — nothing is cached in the JWT, so a role/permission change takes effect on the very next request. See `user.routes.js` for the pattern (`authenticate` → `authorize('roles:manage')` for the admin-only list-users route). `roleRepository.js` has `findByKey`/`listPermissionKeys` helpers. When adding a new permission, update the seed (`db/seeds/00_roles_permissions.js`), not just the schema.
- **Demo account**: `db/seeds/03_demo_user.js` seeds a `demo@example.com` / `DemoOnly123!` account (overridable via `SEED_DEMO_EMAIL`/`SEED_DEMO_PASSWORD`) on the `demo` role, which holds only `:read` permissions across Users/Roles/Settings/Audit Log/example-products/example-sales (see `db/seeds/00_roles_permissions.js`'s `rolePermissions.demo`) — every write/delete/manage action returns 403 for it. Intended for a public-facing deployment (e.g. Vercel) to publish these credentials on the login page so visitors can explore the whole admin without an invite and without being able to break anything. Not `is_system` — deletable/editable like any custom role if a deployment doesn't want it.
- **Audit logging is automatic, not opt-in**: any table's `create`/`update`/`delete` — core or module — should be built on `createAuditedRepository(tableName, moduleName, { idColumn? })` (`src/services/auditedRepository.js`) instead of raw `db(table).insert/update/del`; it writes the `audit_logs` row itself, so nothing calls `auditLogRepository` directly for a create/update/delete. `userRepository`, `roleRepository` (`src/services/roleRepository.js` — both the lightweight dropdown and the full Roles & Permissions CRUD live in this one file, see `backend/.claude/skills/module-registry-pattern/SKILL.md`'s note on the merge), and `settingsRepository` (`src/services/settingsRepository.js`, which passes `{ idColumn: 'key' }` since `app_settings` isn't keyed by `id`) are the worked core examples; `modules/example-products/repository.js`/`modules/example-sales/repository.js` are the optional-module examples. Full API and rules (when `update` does vs. doesn't log, how to redact sensitive fields, when to bypass the wrapper for a non-CRUD action like `password_change`) are in `backend/.claude/skills/module-registry-pattern/SKILL.md`'s "Audit logging is automatic" section — read that before adding a repository, module or not. Three actions are recorded with no field-level diff at all by design (`password_change`, `password_reset`, `password_reset_requested` — see `auth.controller.js`/`user.controller.js`): the frontend's Audit Log detail view (`AuditLogListPage.tsx`'s `NO_DIFF_ACTION_DESCRIPTIONS`) shows a specific message for each of these three instead of a generic "no changes recorded" — add a new entry there for any future no-diff action rather than letting it fall through to the generic message.
- **Validation**: Zod schemas in `validators/`, applied via `middleware/validate.js`. Note there are two validation middlewares with different conventions — `validate(schema)` expects a schema shaped `{ body, query, params }` (used by `lead.routes.js`), while `validateBody(schema)` parses `req.body` directly (used by `user.routes.js`). Match the existing pattern for the route family you're touching rather than mixing them.
- **New route checklist**: add to `routes/`, controller in `controllers/`, Zod schema in `validators/`. Protect with `authenticate` and/or `authorize(...)` as needed; mutating routes relying on cookie auth also need `verifyCsrfToken` (see `user.routes.js`). Note `lead.routes.js` currently has no auth/CSRF protection at all — follow the `user.routes.js` pattern instead if adding new protected routes.
- **New DB table**: migration in `db/migrations/` (timestamp-prefixed filename) via `npm run migrate:make`, then `npm run migrate`. Put query logic in a repository file under `services/` — don't write raw Knex queries in controllers (note `lead.controller.js` currently queries `db('leads')` directly, which is the older pattern; `userRepository.js` is the one to follow for new code). Mutations still go through `createAuditedRepository` per the audit logging rule above, core table or not.
- **`modules/` is exclusively for optional domain features** — never core infrastructure. Users, Roles (`role.*` — both the lightweight `/api/v1/roles` dropdown and the full `/api/v1/admin/roles` CRUD), Settings, and Audit Log are core: every project built on Slokabase needs them, so they live directly under `src/services|controllers|routes|validators`, their migrations/seeds live in `src/db/migrations|seeds` (running with `npm run migrate`'s core `knex migrate:latest` step, never the separate module-migration chain), and they're mounted directly in `app.js` rather than through the module registry loop. Their sidebar entries come from the static `src/config/coreMenu.js` array, merged into `GET /api/menu` by `menu.controller.js` alongside the (optional-module) registry loop.
- **New *optional* feature module**: see `backend/.claude/skills/module-registry-pattern/SKILL.md` for the self-contained-module pattern — `modules/example-products/` and `modules/example-sales/` are reference implementations demonstrating it (including one module depending on another), not something a real project necessarily keeps; delete them if you don't need a Products/Sales domain. The pattern (auto-registered routes/permissions/menu, isolated `knex_migrations_<key>` migration history) is the preferred way to add a genuinely optional domain area without touching `app.js` or `src/db`.
- **Env vars**: add new ones to both `backend/.env.example` and `src/config/env.js` (with a sensible default where possible). `knexfile.js` (used by the Knex CLI) duplicates the connection logic in `src/db/knex.js` with plain `process.env` reads rather than importing `src/config/env.js`, so the CLI doesn't need ESM subpath-import resolution — keep both in sync when changing DB connection options.
- **Hard config vs. soft setting vs. plain constant**: three different places a configurable value can live, and it's a deliberate choice which one, not interchangeable. (1) **Hard config** — `process.env`/`src/config/env.js` — for anything that varies *per deployment* and is either a secret or infrastructure-level (DB credentials, JWT secrets, `FRONTEND_URL`, and the `EMAIL_*` vars as a deployment's *default* SMTP config). (2) **Soft setting** — `app_settings` table via `settingsRepository` — for anything an *admin should be able to change at runtime, without a deploy*: `app_name` (user-facing branding), and the `smtp_*` settings, which are the one case of a soft setting *layered over* hard config rather than replacing it outright — a blank/zero DB value falls back to the matching `EMAIL_*` env var (see the Email bullet above for the exact merge and why `smtp_secure` is the one field that doesn't get a per-call fallback). `support_email` used to live here too; it was removed outright (not just hidden from the UI) once it had no consumer left, the same way `default_timezone`/`items_per_page_default` were before it. If nothing in the codebase ever reads a setting outside its own admin CRUD page, it isn't a soft setting — it's dead weight; see `db/seeds/02_settings.js`'s header comment. (3) **Plain constant** — `src/config/constants.js` (backend) / `frontend/src/constants/*.ts` (frontend) — for a value that's fixed *for this codebase* and not meaningfully "an admin's choice" or "a deployment's choice" (pagination defaults/ceilings). When adding a new configurable value, ask: does this vary per deployment (env var)? Should an admin be able to change it without redeploying, and does something actually consume it beyond its own settings-page row (DB setting)? Otherwise, plain constant.

## Known inconsistencies to be aware of

- `lead.routes.js` still has no `authenticate`/`authorize`/CSRF protection — left as-is since the leads feature is out of scope for the RBAC work; follow `user.routes.js` if it needs locking down later.
